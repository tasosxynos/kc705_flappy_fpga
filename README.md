# Flappy Bird on a Kintex-7 KC705 — bare-metal RTL, no processor

A complete, playable Flappy Bird running on a Xilinx Kintex-7 KC705, written as
**plain Verilog RTL with no processor of any kind** — no MicroBlaze, no Zynq PS,
no soft-core, no firmware. There is also **no Xilinx video IP**: the video
timing generator, the pixel renderer, the colour palette and the HDMI
transmitter bring-up are all hand-written.

Video output is **1920x1080@60, 16-bit YCbCr 4:2:2** over the board's ADV7511
HDMI transmitter. The game itself renders at **640x480 and is displayed once,
centred**, with black margins.

---

## Hardware

| Item | Detail |
|---|---|
| Board | Xilinx Kintex-7 KC705 |
| FPGA part | `xc7k325tffg900-2` |
| System clock | 200 MHz LVDS on `SYSCLK` (`AD12`/`AD11`) |
| Pixel clock | 148.5 MHz, generated by an `MMCME2` |
| Video out | ADV7511KSTZ-P (`U65`) → HDMI connector |
| Controls | SW5 (centre pushbutton, `GPIO_SW_C`) |
| Status | 8 GPIO LEDs |

No external memory, no DDR, no MicroBlaze. The entire game state lives in
flip-flops inside the FPGA.

## Video pipeline

```
SYSCLK (200 MHz LVDS)
  └─ MMCME2 ──────────────────► 148.5 MHz pixel clock
       └─ video_timing.v ─────► 1920x1080@60, hsync / vsync / de (positive sync)
            └─ render_flappy.v ► combinational pixel generator (640x480 space)
                 └─ gfx_palette ► 5-bit palette index → 8-bit Y, Cb, Cr
                      └─ ycbcr422_pack.v ► 16-bit YCbCr 4:2:2
                           └─ HDMI_D[15:0] ► ADV7511 (U65) ► TMDS ► HDMI
```

* The 640x480 game image is placed once in the centre of the 1920x1080 raster
  (offset 640 columns, 300 lines). Everything outside the window is forced to
  video black, so the game never tiles or scrolls past its own screen.
* Over the 16 data lines, **the upper byte carries luma and the lower byte
  carries chroma** (`HDMI_D[15:8]` = Y, `HDMI_D[7:0]` = Cb/Cr), matching the
  KC705 schematic's wiring into the transmitter's `D[23:8]`.
* Pin assignments are taken from the KC705 documentation (UG810) HDMI pin table.

## ADV7511 bring-up

The ADV7511 is a real transmitter chip, not a passive PHY, so it must be
configured over I2C before it produces any output. All of that is done in RTL
(`i2c_master.v` + `adv7511_init.v`): a hand-written I2C master runs a 49-step
register sequence at power-up, reaching the transmitter at address `0x39`
through the board's I2C mux (`0x74`, channel 5).

Two details are worth recording, because both cost real debugging time:

* **Open-drain polarity.** The board wires SCL/SDA as true open-drain, but the
  Xilinx `IOBUF` primitive uses `T` as a *tri-state* enable (T = 1 → Hi-Z), while
  the master's `oe` signals mean the opposite (oe = 1 → pull low). Wiring `T`
  straight from `oe` inverts both bus lines; the fix is `.T(~scl_oe)` /
  `.T(~sda_oe)`.

* **Input data mapping.** With `0x15 = 0x01` (16-bit YCbCr 4:2:2, separate
  syncs), the transmitter's *style* register `0x16` and its 4:2:2 alignment
  register `0x48` together decide which incoming pins the transmitter treats as
  luma vs chroma. The combination that produces correct colour on this board is:

  ```
  0x16 = 0x3C   // style 3
  0x48 = 0x08   // 4:2:2 -> 4:4:4 conversion, right justified
  ```

  This was found empirically with a built-in **sweeper**: a diagnostic build in
  which each press of SW5 rewrote the two registers with the next candidate
  combination (3 styles × 3 alignments), with the LEDs displaying the active
  index, and the screen showing a known black→white ramp. The sweep is
  disabled in the game build so the button is free for gameplay.

`adv7511_status.v` keeps monitoring the link afterwards (PLL lock, HPD, monitor
sense, I2C NACKs) and exposes it on the LEDs.

## The game

`game_flappy.v` is the complete game logic — states, physics, pipes, collision,
scoring and a small pseudo-random gap generator. All movement is integer pixel
based and updates **once per video frame**, which gives the chunky 8-bit
arcade feel.

| State | Behaviour |
|---|---|
| `IDLE` | Title screen, bird bobbing, first flap starts play |
| `PLAY` | Gravity, flap impulse, scrolling pipes, scoring |
| `FALL` | Collision happened, bird drops to the ground |
| `OVER` | Game-over screen, first flap restarts |

Game world: bird fixed at x = 96 (16x12 sprite), three pipes 64 px wide with a
140 px gap on a 960 px cycle scrolling 2 px/frame, ground at y = 400.

`render_flappy.v` is a purely combinational pixel generator with a fixed layer
priority: bird → UI text → score → pipes → clouds → hills → ground → sky.
Sprites and glyphs come from `gfx_roms.v` (generated by `tools/gen_gfx.py`).

### Where the score lives

**In plain flip-flops, not BRAM.** The score is three 4-bit registers holding
BCD digits:

```verilog
output reg [3:0] score_h,   // hundreds
output reg [3:0] score_t,   // tens
output reg [3:0] score_o    // ones
```

They are incremented when the bird passes a pipe, with a per-pipe "already
counted" flag so each pipe scores exactly once, and they are rendered by the
same 5x7 glyph font as the rest of the text. There is no frame buffer and no
memory of the screen anywhere in the design: every pixel is computed on the fly
from the current game state as the beam passes.

## Resource usage

From the implementation report (`xc7k325tffg900-2`):

| Resource | Used | Available | % |
|---|---|---|---|
| Slice LUTs | 1,161 | 203,800 | 0.57 |
| Slice Registers | 470 | 407,600 | 0.12 |
| Block RAM Tiles | 0.5 | 445 | 0.11 |
| DSPs | 0 | 840 | 0.00 |
| Bonded IOBs | 36 | 500 | 7.20 |

That single half block-RAM tile is used by one of the read-only graphics
tables; the entire game state is in registers.

## Building

Vivado 2025.2:

```sh
vivado -mode batch -source build.tcl
```

The resulting bitstream is `build/kc705_flappy.runs/impl_1/kc705_flappy_top.bit`.

## Programming

With `openFPGALoader`:

```sh
openFPGALoader -b kc705 kc705_flappy_top.bit
```

## Controls and LEDs

**SW5** makes the bird flap — and is the only control. It is used for
everything: start, flap, restart.

The eight GPIO LEDs are a bring-up diagnostic panel:

| LED | Meaning |
|---|---|
| 0 | MMCM locked |
| 1 | I2C init sequence complete |
| 2 | monitor sense (`0x42[5]`) |
| 3 | hot-plug detect (`0x42[6]`) |
| 4, 5 | `0xD6` read-back bits 7 and 6 (both 1 = correct) |
| 6 | transmitter input PLL lock (`0x9E[4]`) |
| 7 | I2C NACK seen — **off is correct** |
